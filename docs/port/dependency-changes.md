## sparsebitfield — C7 (escalation point #1, resolved)

### Problem
`sparsebitfield==0.2.5` does not build on Python 3.13.  The shipped
Cython-generated `cimpl/field.c` references CPython internals that were
removed/changed in 3.13:

- `PyLongObject.ob_digit` — removed (3.12 removed `ob_digit` in favour of
  opaque `PyLongObject`).
- `_PyLong_AsByteArray` — signature changed (extra argument).
- `_PyGen_SetStopIterationValue` — removed from the public C API.

Impact: 4 core benji modules (`benji.benji`, `blockuidhistory`, `commands`,
`nbdserver`) and 10 of 16 unit-test files fail at collection time.

### Fix
The `.pyx` source is almost clean.  The only incompatibility is a Python-2
`long` reference in `SparseBitfield.load()`:

```diff
-            if isinstance(item, (int, long)):
+            if isinstance(item, int):
```

Behaviour is identical on Python 3 (where `long` was merged into `int`).
Regenerating `cimpl/field.c` from the patched `.pyx` with Cython ≥ 3.0
(`language_level=3`) yields 3.13-compatible C.  The regenerated output uses
a version-guarded `__Pyx_PyLong_Digits` macro (`long_value.ob_digit` on
Python ≥ 3.12, `ob_digit` on older) so the same source compiles across
versions.  It builds with just a C compiler + setuptools; **Cython is not
required to install the vendored copy.**

### Verification
- `sparsebitfield` imports on Python 3.13.5.
- Upstream test suite (`test/test_bitfield.py`): **17/17 passed**.
- Smoke check (`add`/`in`/`len`) OK.

### Packaging decision (vendored)
The patched source is vendored under `vendor/sparsebitfield-0.2.5/` with
its `cimpl/field.c` regenerated by Cython 3.0.11 and the package version
bumped to `0.2.5.post1` so the patched build is distinguishable from the
broken PyPI 0.2.5.  `setup.py` pins `sparsebitfield>=0.2.5.post1,<1`, which
the PyPI 0.2.5 cannot satisfy, so pip cannot silently fetch the broken
build.  Provenance of the source change is preserved as
`patches/sparsebitfield-0.2.5-py313.patch`; a full description lives in
`vendor/README.md`.

Install order:
```bash
pip install vendor/sparsebitfield-0.2.5/ && pip install -e .
# or, equivalently:
pip install --find-links vendor/ -e .
```

### Upstream plan (target)
`elemental-lf` maintains both benji and sparsebitfield.  The final form is
an upstream `sparsebitfield>=0.2.6` release on PyPI containing the
`long→int` fix and a Cython-≥3.0-regenerated `cimpl/field.c`.  Once
published: remove `vendor/sparsebitfield-0.2.5/`, delete
`patches/sparsebitfield-0.2.5-py313.patch`, and re-pin
`sparsebitfield>=0.2.6,<1` in `setup.py`.

### License
sparsebitfield is **BSD-2-Clause** — compatible with benji's LGPL-3.0-only.
Original copyright holders (Steve Stagg, Lars Fenneberg) retained.

## ruamel.yaml — C2

### Problem
`ruamel.yaml>0.16,<0.17` (0.16.13) used `pkg_resources.declare_namespace('ruamel')`
(deprecated, slated for removal) and triggered a `DeprecationWarning` on import
under Python 3.13. Separately, `src/benji/config.py:14` imported
`pkg_resources.resource_filename`, also deprecated.

ruamel.yaml 0.18 **removed** the top-level `load(stream, Loader=...)` helper —
calling it now raises `AttributeError` (not merely a warning), so the pin bump
requires an API change in `config.py`.

### Fix
- `setup.py` pin changed to `ruamel.yaml>=0.18,<0.19`.
- `src/benji/config.py`: the three `ruamel.yaml.load(..., Loader=ruamel.yaml.SafeLoader)`
  call sites (schema load, config-file load, ad-hoc config load) replaced with a
  single module-level `ruamel.yaml.YAML(typ='safe')` instance (`_YAML`) and its
  `.load()` method. Safe loading produces plain `dict`/`list`/`str`/`int`/
  `float`/`bool`/`None` with identical parsing semantics to the previous
  `SafeLoader`, so config and schema content is parsed byte-for-byte the same
  as on 0.16.
- `from pkg_resources import resource_filename` → `from importlib.resources import files`
  (PEP 420). Schema discovery now anchors on
  `files(__name__.rsplit('.', 1)[0]) / 'schemas'`, which resolves to the same
  directory as the former `resource_filename(__name__, 'schemas')` (the
  directory holding `config.py` joined with `schemas` = `src/benji/schemas`).

### Parity note
Config and schemas are input-only metadata; they are not part of the backup
data path. The validated scalar values that flow into backup metadata (block
size, compression settings, etc.) come from the config file content, parsed
identically by both loader versions. No golden-master parity risk.

### Verification (Python 3.13.5, ruamel.yaml 0.18.17)
- `src/benji/tests/test_config.py`: **14/14 pass** in isolation.
- `src/benji/tests/test_store.py::BenjiStoreTestCaseSQLLite_File`: **58/58 pass**.
- No more `pkg_resources` or `ruamel.yaml.declare_namespace` DeprecationWarnings.

### License
ruamel.yaml is **MIT** — compatible with benji's LGPL-3.0-only.

## pyparsing + attrs — C3 (escalation #3, resolved)

### Problem
`pyparsing>=2.3.0,<3` (2.4.7) imported the removed `sre_constants` module,
which raises a `DeprecationWarning` on Python 3.12+ (the module is slated
for removal). pyparsing 3.x dropped that import and deprecates the
camelCase API aliases in favour of snake_case, emitting
`PyparsingDeprecationWarning` (a subclass of `DeprecationWarning`) when
the old names are used at runtime.

`attrs>=21.4.0,<22` (21.4.0) had a very stale upper bound. The core benji
package does **not** use `attrs` directly; the only consumer is the
`images/benji-k8s/k8s-tools/` helper, which already uses the modern
`attrs.define(kw_only=True)` API (compatible with attrs 23/24).

### Fix
- `setup.py` pins: `pyparsing` → `>=3.1,<4` (installed 3.3.2);
  `attrs` → `>=23,<25` (installed 24.3.0).
- `src/benji/database.py` (`_QueryBuilder` version-filter grammar — the
  only pyparsing consumer in the codebase): migrate the deprecated
  camelCase calls to their snake_case equivalents. The grammar structure,
  tokens and parse actions are unchanged, so parsing is identical:
  - `enablePackrat()` → `enable_packrat()`
  - `setParseAction(...)` → `set_parse_action(...)`
  - `replaceWith(...)` → `replace_with(...)`
  - `removeQuotes` → `remove_quotes`
  - `infixNotation(...)` → `infix_notation(...)`
  - `parseString(..., parseAll=True)` → `parse_string(..., parse_all=True)`
  - The non-deprecated names (`quotedString`, `pyparsing_common`,
    `opAssoc`, `Regex`, `Keyword`, `Literal`, `ParseException`,
    `ParseFatalException`) are kept as-is.
- `retentionfilter.py` uses plain `re`, not pyparsing, and is unaffected.
  escalation #3 (verify retention/version grammar on pyparsing 3.x) is
  resolved: the version-filter grammar parses 19/19 representative
  expressions cleanly under `-W error::DeprecationWarning` and still
  rejects invalid expressions.

### Parity note
The filter grammar is only used to translate a `--filter` expression into
a SQLAlchemy query at runtime; it does not touch the backup data path or
written metadata. No golden-master parity risk.

### Verification (Python 3.13.5, pyparsing 3.3.2, attrs 24.3.0)
- 19/19 filter expressions parse with zero warnings; invalid expressions
  still rejected.
- `test_retentionfilter.py` 19/19, `test_config.py` 14/14,
  `test_store.py::SQLLite_File` 58/58, `test_aes_keywrap`/`test_blockhash`/
  `test_blockuidhistory`/`test_dicthhmac`/`test_transform_ecc` 17/17 —
  all pass in isolation.
- `sre_constants` and pyparsing camelCase `DeprecationWarning`s are gone.
- pylint: no new errors (9.88/10; pre-existing E1102 untouched).

### License
pyparsing and attrs are both **MIT** — compatible with benji's LGPL-3.0-only.

## structlog + diskcache — C9 (pin tightening + CVE documentation)

### structlog — pin tightened, no code change
- Pin: `>=19.1.0` (no upper bound) → `>=19.1.0,<27` (installed 26.1.0).
- Rationale: benji imports the private API
  `from structlog._frames import _find_first_app_frame_and_name` in
  `src/benji/logging.py:16` and `src/benji/helpers/utils.py:11` (used by
  custom structlog processors that add source context — file, line,
  function — to log events). There is no public API equivalent. The
  upper bound `<27` protects against a future major version removing or
  moving the private function. structlog 26.x still exports it from both
  `structlog._frames` and `structlog.processors`.
- No deprecation warnings on Python 3.13.5. `TimeStamper(utc=True)` is
  not deprecated.
- License: **MIT** — compatible with LGPL-3.0-only.

### diskcache — pin tightened, CVE-2025-69872 documented (no fix available)
- Pin: `>=3.0.6` (no upper bound) → `>=3.0.6,<6` (installed 5.6.3, the
  latest version).
- **CVE-2025-69872** (CVSS 3.1 9.8 CRITICAL per CISA-ADP):
  DiskCache through 5.6.3 uses Python pickle for serialization by default.
  An attacker with write access to the cache directory can achieve arbitrary
  code execution when a victim application reads from the cache (CWE-502
  Deserialization of Untrusted Data). Published 2026-02-11; no fix version
  exists — 5.6.3 IS the latest and IS vulnerable.
- **Risk assessment for benji:**
  - benji uses diskcache in two places: `Cache` for the NBD block cache
    (`benji.py:1284`) and `FanoutCache` for the storage read cache
    (`storage/base.py:520`). Both store only data that benji itself wrote
    (block bytes + metadata dicts) — not untrusted external input.
  - The attack requires write access to the cache directory (configured by
    the admin via `nbd.blockCache.directory` / `readCache.directory`). This
    is a local attack vector, not a remote exploit through backup data.
  - **Mitigation:** the cache directory must be protected by filesystem
    permissions (owner-only read/write, e.g. `0700`). This is a deployment
    responsibility, not a code change. When an upstream fix is released
    (likely a non-pickle serialization option), upgrade and re-pin.
- **No code change made** — replacing diskcache or switching to a custom
  non-pickle serializer would be a scope change (AGENTS.md rule 3: "No
  scope creep") and the CVE has no fix version to upgrade to. The risk is
  documented and the pin is tightened to prevent unexpected major version
  bumps.
- License: **Apache-2.0** — compatible with LGPL-3.0-only.

### Other C9 deps — no change needed
- **dateparser** `>=1.1.1,<2` (installed 1.4.1): works on Python 3.13,
  no deprecation warnings. Used in `BenjiDateTime.process_bind_param`
  (`database.py:72`) for parsing date strings from config. Parsing
  behaviour verified identical. License: **BSD-3-Clause**.
- **semantic_version** `>=2.8.1,<3` (installed 2.10.0): works on Python
  3.13, no deprecation warnings. Used in `config.py`, `database.py`,
  `versions.py`, `storage/base.py`. (The package is in maintenance mode
  in favour of `semver`, but works fine and is still maintained.) License:
  **BSD-2-Clause**.
- **colorama** `>=0.4.1,<1` (installed 0.4.6): works on Python 3.13,
  no deprecation warnings. License: **BSD-3-Clause**.

### Verification (Python 3.13.5)
- All C9 deps import cleanly under `-W error::DeprecationWarning`.
- `test_store::SQLLite_File` 58/58 + 6 other test files 36/36 — all pass
  under `-W error::DeprecationWarning`.
- pylint: setup.py 10.00/10.

## bottle — F7 (escalation point, unresolved)

### Problem

`bottle>=0.12.16,<0.13.0` (pinned in `setup.py` `rest-api` extras) fails to
import on Python 3.13. Bottle 0.12.x uses `import cgi` at the module level
(`bottle.py:38`). The `cgi` module was removed in Python 3.13
(PEP 594 — dead standard library). This blocks the REST API smoke test (F7).

### Impact

- REST API server cannot start on Python 3.13 (`rest-api` subcommand).
- F7 tests (`test_rest_api.py`) skip gracefully via `importlib.util.find_spec`.
- This is a known escalation point (PORTING-TASKS.md §Eskalation).

### Potential fixes (not yet applied)

1. **Upgrade bottle to ≥0.13** — the 0.13 development branch removed the `cgi`
   dependency. Requires pin update in `setup.py` and compatibility testing.
2. **Patch bottle** — vendor a patched version that replaces `cgi` usage with
   `email.utils` / `html.escape` equivalents.
3. **Replace bottle** — migrate REST API to FastAPI/Starlette. Out of scope
   for this port (REST API is frozen variant b).
